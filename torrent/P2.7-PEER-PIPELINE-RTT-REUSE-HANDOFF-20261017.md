## 目的与事实边界

本轮推进真正作用于网络侧的请求管线、选择 Peer 策略和连接保留，不只是修正速度显示。变更已经进入工作区，但**不代表运行中的 Spring Boot JVM 自动应用**；没有对原生任务实施强制重启、进度清零、Checkpoint 删除或公共监听更改。公网 2x5 分钟 qBittorrent A/B 必须在完整且同条件的种子测试环境中另行验证，不可将实验 Mock 测试或理论窗口容量写成公网吞吐增益。

## 1. BEP3 Block 请求队列持续补充（生产路径）

文件：`backend/src/main/java/cc/ivera/magnet/engine/piece/PeerBlockRequestWindow.java`

- 旧行为：预先申请 16 个 16KiB Block；最初 4 次 ACK 后，目标窗口立即可能缩为 4，导致新请求根本未补齐。即使 TCP 有能力继续接收也会出现“空请求队列”。
- 新行为：在前 16 次有效 ACK 的预热期维持 16 个请求的目标容量，并持续在 ACK 后补充到目标；之后依据近期 payload 速率 EWMA 和约 2 倍 Block RTT 自适应，最低 8 个，硬上限始终为 64（1MiB）。
- 保留每个 Block 的请求时间、独立超时、重复/伪造 Block 拒绝及最终完整 Piece SHA-1 校验。慢 Peer 仍可能降低请求容量和失去 Piece 所有权。
- 新增 `lastObservedRttNanos()`：与平均 RTT 分离，供任务内最近 RTT P95 使用。请求队列 API 容量展示改为目标窗口，但不允许小于已实际在途请求量，避免扩缩容瞬间展示负数或抛参数异常。

## 2. 快速与慢 Peer 的动态选择（生产 Piece-first + Peer-centric）

文件：`backend/src/main/java/cc/ivera/magnet/engine/piece/PeerHealthTracker.java`

- 旧策略给予旧 TCP Actor 约 4 亿权重，显著高于实际有效载荷速率，导致已建立但很慢的 Peer 容易长期压过快 Peer。
- 新策略：按**完整 SHA-1 验证后的 Piece 传输速率 EWMA**、任务内最近 Block RTT P95、失败历史、成功证明、Bitfield 确认、同一 Actor 的 TCP 连接亲和性和 in-flight 负载综合排序。
- 正常复用依然加分，但控制在约 800 万级，吞吐大幅领先或 RTT 明显更低的 Peer 应能抢回任务。
- 连续出现相对较慢的已验证 Piece 时只增加软降权，不将慢 Peer 永久禁用；如果它是唯一具有稀有 Piece 的 Peer，仍能申请对应 Piece。
- `PeerHealthTracker` 上一轮健康度迁移保留任务内 EWMA、RTT 和软降权；不同用户、Task UUID 无法继承这些记录。
- `PieceDownloadCoordinator.fetchWithHealth` 在 fetch 完成或失败后向健康选择器反馈本任务当前 Peer 的 Block RTT 统计，不阻断正常的 Piece/fence/Checkpoint 流程。

## 3. 真实 Block RTT P95、Socket 保留策略

新增文件：`PeerLatencyWindow.java`。  
变更：`PeerRoundConnectionPool.java`、`PeerPieceDownloadSession.java`。

- 每个 `TaskIdle` 按 Peer endpoint 保留最近 32 次 **Block Request → Block 响应**延迟；计算 nearest-rank P95，界限 32 个 long 样本，内存可控，任务结束自动丢弃。
- 现有 API 的 RTT 分位数从原来的 RTT EWMA 采样改为真正的单次 Block RTT 采样，仍采用直方图**近似值**展示全任务 P50/P95。
- Task Actor 向健康选择器反馈 endpoint 的 P95，结合吞吐降权。无可用样本时不做猜测。
- 跨轮 TCP 空闲保持时间按观测指标区分：P95 >= 800ms 约 15 秒退役；P95 <= 350ms 且确实发生过 Socket reuse 的 Task 约 75 秒；其余维持原来 30 秒。此调整不会跨用户共享 Socket；任务取消及已发现的脏连接仍立即关闭；下一轮发现远程 Socket 已关闭或写/读失败时照常回收。
- 缓存依然有 `PER_THREAD_CAP` 和 `TASK_IDLE_CAP` 硬上限，并非无限维持连接。数据未校验成功时不增加吞吐信用。

## 4. 本轮新增测试

- `PeerBlockRequestWindowTest.firstRepliesNeverCollapseWarmPipelineFromSixteenToFour`：16 个 Block 的预热目标保持，连续 4 个 ACK 后能够及时补发 4 个新请求。
- `PeerHealthTrackerTest.fasterPeerBeatsStickySocketAndHighRttPeerWithoutHardBanningSlowSources`：快 Peer 的已验证速度 + RTT 超过粘滞连接权重；唯一持有稀缺 Piece 的慢 Peer 仍可分配；健康数据仅在同一 Task 中跨轮继承。
- `PeerLatencyWindowTest`：最近 32 Block P95、超慢旧样本淘汰、空样本处理。
- `PeerRoundConnectionPoolTest.fastReusedPeersKeepSocketsLongerButSlowP95RetiresEarly`：证实 15/30/75 秒有界连接缓存预算。
- 延续 `ParallelPeerRoundReuseTest`、`PeerCentricCoordinatorIntegrationTest`、`NativePeerRequestTelemetryTest` 验证真实 TCP 复用、Bitfield、任务独立与遥测无泄漏。

源码改造的自动测试只证明边界正确和功能可用，**不能证明公网速度比 qBittorrent 更快**。下一步应先按 `torrent/benchmarks/measure-5min.ps1` 对公开 Ubuntu ISO 两个干净的下载任务分别采集 300 秒指标，再依据下面的观测策略决定是否继续调整：
- Occupancy 低、RTT 低、Peer 已经验证快：优先检查请求补充、Bitfield 可用性和 Pipe 是否饱和；
- Occupancy 高、RTT P95 高、网络 payload 低：优先降权该 Peer、检查拥塞/超时/错误率；
- 新 TCP 建连数持续高、跨轮复用率低且 RTT 良好：优先检查 Worker Actor 生命周期、缓存 TTL、Peer 重新选择；
- 轮内缓冲已校验数据过高但 payload 正常：检查上轮 P2.6 分组提交时间/容量和磁盘延迟，而不是盲目提高连接数。
