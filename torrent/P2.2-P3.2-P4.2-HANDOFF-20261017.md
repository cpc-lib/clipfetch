## P2.2 具体行为

1. 仅在现有授权连续任务已拥有 `TaskPeerActorPool` 的情况下走新的 Peer-centric Piece 派工；非连续/一次性任务保持旧调度。
2. 各 Actor 网络线程原子地从 `PeerCentricPieceQueue` 领取 `(Peer, Piece)`，一个 Piece 在本轮只有一个主请求所有者，不产生跨用户、跨任务请求共享。
3. `PeerHealthTracker` 优先选择自己已连接且经过完整 SHA-1 校验的 Peer；根据其 Bitfield 与 in-flight 避免将工作分给明确没有该 Piece 的 Peer。
4. 传输失败、断线、退避后仍使用既有 `fetchWithHealth` 重试；成功的 Piece 继续交给原 Worker owner 单线程提交文件与数据库。没有绕过租约、Fence 或写入校验。
5. 新增日志：`native_peer_centric` 与 `native_peer_centric_result`，能观察激活 Actor、计划 Piece、实际分配、剩余 Piece、提交与失败数。
6. 动态刷新后新 Peer 可参与后续重试；最多 4 次 Peer 尝试，不再用初始 Peer 列表大小决定重试上界。

## P3.2 Block 超时回收

- 原先 `PeerBlockRequestWindow` 已记录每个未完成 Block 的发送时间、超时和 RTT。
- 本轮给出 `pendingBlocks()` 快照；当 `PeerRoundConnectionPool` 或 `PeerPieceDownloadSession` 的当前 Socket 接收超时时，最多 64 个剩余请求以 BEP3 `CANCEL` 消息发送（index / begin / length 与原 Request 一致）。
- CANCEL 是尽力行为：Peer 可能已断链；发送失败被加入主异常的 suppressed 列表而不掩盖真实故障。原代码随后关闭故障 Socket。
- 之前合法返回的 Block 在内存中保留，只对缺失 Block 重试；完整 Piece 的哈希不正确仍清空缓冲，不能将部分 Block 计入安全进度。

## P4.2 uTP 可靠状态边界

- 现有 `UtpPacketCodec` 实现 BEP29 包头与严格边界验证，`UtpCongestionWindow` 实现有界拥塞窗口与延迟反馈。
- 新增 `UtpReliableChannel`（独立于下载任务、不向公网绑定端口）：同连接 ID 检查、接收窗口、按序交付、乱序最多 64 包和 64*1200 bytes、最多 128 个未确认发送包；用 KARN 规则避免重传 ACK 污染 RTT；超过次数中断会话。
- 非法未来 ACK 不得释放从未发送的数据；重复和过旧 DATA 不会再次上交。
- 本地 `UtpLoopbackDatagramTest` 通过真实环回 UDP 传送已编码数据报、故意模拟一次丢包、超时重传并确认 ACK。
- 尚缺可正式启动的完整 uTP 可靠传输堆栈，因此 **不添加默认启动 UDP listener，不开放防火墙，不向用户宣称支持 uTP 下载**。

## 后续高优先级

1. **P2.3 真正 per-Peer Block mailbox**：把同一个 Peer 的多个 Piece Block 请求并行交错到一条 Socket 上；实现 HAVE/CHOKE 的异步处理和 Block 级全局 Picker，仍需按 User/Task 隔离。
2. **P3.3 真实 end-game 多 Peer Block racing**：唯一主租约 + 至多一个备份抢占、优先尾部慢 Block、收到首个有效 Block 后 CANCEL 其他 Peer、隔离伪造重复数据并量化冗余传输。
3. **P4.3 完整 uTP transport**：BEP29 SYN/STATE ACK state、UDP connection demultiplex、可靠字节流 adapter 和 MTU 探测；完整单元+loopback+libtorrent 互操作测试通过后才考虑启用实验开关。
4. **统一 Ubuntu ISO 基准**：相同网络同一官方种子，不要同时运行 qBittorrent 与 Native 抢 Peer/吞吐；分别统计至少 5 分钟的 payload B/s、verified B/s、Peer 有效率、连接复用率、取消/恢复耗时、p95 Block 时延及重复流量占比。
