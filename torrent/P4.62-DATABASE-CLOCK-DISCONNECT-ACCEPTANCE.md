# P4.62 数据库权威时间源与 MySQL 断连验收

## 代码修复
- `TorrentNativeWorkerInstanceMapper.databaseTime()` 提供数据库 `CURRENT_TIMESTAMP`，`databaseNow()` 转为 LocalDateTime；MySQL 与 SQLite 时间由当前连接的数据库提供，避免依赖 JVM 本地墙钟。
- `NativeWorkerInstanceHeartbeat` 的 register、renew、isHealthy 全部改用 mapper.databaseNow。
- `NativeExpiredOwnerFenceService` 恢复隔离前租约判断改用 mapper.databaseNow，仍在 Checkpoint 文件锁和独立数据库事务内检查。
- 三项时间敏感 Mapper SELECT (`databaseTime/isLive/isExpired`) 显式 `flushCache=true,useCache=false`，禁止在同一个 MyBatis SqlSession 内复用旧租约判断；真实断连测试发现原缓存返回旧健康状态，这是本轮实际修复的缺陷。

## 验收
- SQLite 自然租约到期与四路并发竞争专项通过。使用数据库时间秒精度后，测试等待延长到 2.5 秒，以跨过秒级截断边界。
- MySQL 8.0 Docker 临时隔离容器 `clipfetch-mysql-clock-it`，初始化租约表 V19；新增 opt-in `NativeMysqlDisconnectIT`。
- 真实测试：注册并确认有效心跳，执行 `docker pause` 断连；旧 Worker `isHealthy` 返回 false，隔离回调恰好一次；随后 `docker unpause`，旧 Worker 继续不健康、不续期；新数据库会话确认该实例在租约未自然过期时数据库可看到 ACTIVE，但旧 JVM 不得自动复活。
- 断连期间原 MyBatis Session 的连接可能变为不可用，恢复后采用新的会话读取数据库；不等同于旧连接能自动恢复。
- 专项真实断连测试与 Maven 全量 `mvn -f backend/pom.xml -q test` Exit Code 0。

## 风险与限制
- 本轮依赖数据库 CURRENT_TIMESTAMP 和数据库会话时区；多数据库节点必须统一时区配置。当前实现读时间与更新之间存在一次往返；数据库主从切换与事务快照隔离仍需专门验证。
- 本次验证是 Docker pause/unpause 的同机 MySQL 容器故障注入；不是两台真实服务器网络分区、代理丢包或数据库 HA 主从切换演练。
- Native 自动接管保持关闭。NFS/SMB 仍拒绝。不接通公网 Peer。
- 长期建议把租约时间计算、有效性判断和续期原子地放在同一 SQL 内，以数据库 NOW() 为判定值，同时统一 SQLite/MySQL 的 SQL 方言，避免跨会话时区差异。
