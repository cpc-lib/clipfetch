# ClipFetch Native 下载优化：限时 / 限容量的可靠 Piece 分组提交

**日期**：2026-10-17  
**工作区**：`D:\release\clipfetch`  
**阶段**：libtorrent 吞吐调优，P2.6 — Bounded Checkpoint Group Commit

## 发现的问题

原 `PieceDownloadCoordinator.parallel` 设置 `commitGroupPieces=64` 后，最多等待 64 个已校验 Piece 才做一次 Manifest 发布 + DB CAS。以前只在没有完成 Future 超过 5 秒时才会提交尾部数据。若持续有零星新 Piece 返回，但始终未达到 64 Piece，则前面已校验并 fsynced 的数据仍长时间未被记入持久进度。大 Piece（例如 2.5 MiB）甚至可能有超过 100 MiB 等待发布。

这不等同于网络速度慢，却会延迟可恢复进度和 UI 已校验提交值，也会增加重启/异常时需要重新扫描的数据量。原有的 64-Piece 分组有降低 Manifest + DB CAS 频率的意义，不能直接退化为逐 Piece 提交。

## 本轮落地

- 新增 `NativeGroupCommitPolicy.java`，负责三个约束：
  - 达到现有配置的 `commitGroupPieces`，保持原批量语义；
  - 暂存已校验数据达到 **16 MiB**，即使没有达到 Piece 数阈值也发布；
  - 首个已暂存 Piece 最多等待约 **2 秒**，即使后续 Peer 全部慢下来也会发布；
  - 最后一批永远提交剩余校验数据。
- `PieceDownloadCoordinator.parallel`：
  - 由原本最多 5 秒的无完成结果等待，改为根据限时提交截止点最多 200ms / 空闲最多 1 秒的有界 poll；
  - 到期时先由**任务 Owner 线程**执行组发布和 DB CAS，然后才继续等待网络；
  - 限容量组满后立刻发布，避免若干大 Piece 数据长时间停留在待发布区。
  - 每次成功提交后重置组的起始时间与计数；异常时沿用现有 `discardStagedGroup()` 清理策略。
- `PieceDownloadCoordinator.parallelMultiplexed`（实验开关路径）也采用相同的分组容量/数量约束，尽量保持提交语义一致。
- 没有改动 `VerifiedPieceCheckpoint` 的 SHA-1、fsync、Manifest 及 fenced CAS 的职责：未经整 Piece 校验的数据不能进入 Verified Store。所有发布都在原 Owner 线程执行，未改变租约/用户隔离机制。

## 新增回归测试

- `NativeGroupCommitPolicyTest` 验证配置数量、16MiB、2秒、最终尾部及非法参数。
- `ParallelPieceDownloadCoordinatorTest.publishesTimedPartialGroupBeforeSlowTailPeersFinish` 用慢 Peer 的可控栅栏模拟后续 Piece 全部等待，验证已校验的第一个 Piece 在慢 Peer 放行前已经由 Owner 线程持久化发布。
- 既有 `all64PieceFetchesCanRunConcurrentlyAndCommitOnlyOnOwnerThread` 仍保证 64 个小 Piece 只进行一次提交，不额外增加正常快速批次的数据库 CAS。
