项目：`D:\release\clipfetch`
基线 HEAD：`1293acd`（feature）

## 修复的网络瓶颈

过去只有 `PeerBlockMailbox.ENDGAME_REMAINING=16` 及以内才允许冗余请求。大 Piece 的数十个 Block 已分配给一个 Peer 后，即使另一条认证 TCP 连接已空闲，也只能等待慢 Peer 回复、整条连接超时或整轮超时。并且任务级 Mailbox 的 `claim` / `hasPotentialWork` 热循环会反复遍历已完成 Block；TCP Actor 在没有可分配请求时每 2~15ms 重建 Peer Bitfield、扫描大量 Block，造成不必要的 CPU 消耗。

## P3.0 主要实现

### 非 End-game Block 租约转移

`PeerBlockMailbox.reassignOverdue(peer,availability,nowNanos,max)` 是 synchronized 的任务本地转换：

1. 当前未完成 Block >16 且接收 Peer 仍有请求窗口空位时，查找被其他 Peer 持有且已超过 RTT 计算的请求时限（`max(2s,min(8s,4x RTT))`）的 Block。
2. 每次调度最多转移 8 个；旧 Peer 的在途数量减一，新 Peer 的在途数量加一；接收方成为**唯一主租约**；原有 End-game 一主一备机制继续独立运行。
3. 往旧 Peer TCP Actor 的 CANCEL 队列写入对应 BEP3 `CANCEL`，新 Peer 发送 BEP3 `REQUEST`。`PeerRoundConnectionPool.runMailbox` 每 ~250ms 至多评估一次超时转移，不扫描全部历史完成 Block。
4. 已发生过超时转移的旧 Peer 被标记为不可继续分配新 Block，也不能反向抢回健康 Peer 的新租约；但它仍能完成此前合法持有的其他 Block。
5. 已撤销 Block 的迟到 `PIECE` 被识别为已授权旧请求的 `DUPLICATE`，**不会**进入 assembler / SHA-1 / checkpoint / durable bytes；未获任何旧租约的伪造 Block 仍被拒绝。
6. 受 CANCEL/迟到响应风险影响的 TCP Socket 标记为禁止跨轮复用。原 Worker/Task Owner、Epoch/Fence、InfoHash、PeerID、Piece SHA-1 与提交 CAS 均未绕过。
7. 一个 Block 的旧租约记录有固定上限（最多 4 个不同 Peer），避免无限流量扩散。若没有其他可用 Peer，则保持现有超时/重连/后续轮次逻辑，不伪造传输完成。

### 数据驱动的 CPU 减负

- `PeerBlockMailbox` 增加 synchronized `unclaimed` 数量和 `remainingByPiece` 索引；增量更新认领、断连交回及最终接受状态。
- `unfinished` LinkedHashSet 只保留未完成 Block：新请求、End-game、超时租约和断连的扫描不会再遍历整个历史 `MAX_BLOCKS=32768`。
- `hasPotentialWork` 只检查尚有 Block 的 Piece，不逐 Block 扫描；超时退休的 Peer 不被当作可接管的新工作 Actor。
- `PeerRoundConnectionPool` 在本连接 Bitfield / HAVE 版本未改变时复用已解析的 Peer Piece Availability，避免 TCP Actor 每次热轮询重建所有 Piece 的位图。
- 实验路径可在 `native_multiplexed` 日志中查看 `transferredBlocks` 与 `staleBlocksDropped` 计数。它们是 Task/Round 内计数，不代表增加的持久有效数据，也不替代公共吞吐测速。
