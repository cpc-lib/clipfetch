# P4.56 MySQL 双 JVM 提交/崩溃注入验证

## 已实现
- 使用临时 MySQL 8.0 实例（本机端口 33316），依次应用 V13、V19、V20、V21。
- `NativeMysqlTwoJvmCommitIT` 使用两个独立 Java 子 JVM、真实 MySQL JDBC 连接、同一 Checkpoint 文件锁。
- 注入 CRASH：事务 UPDATE task + INSERT audit 但不提交，先创建旁观 JVM 排队等锁；杀死事务进程后，旁观 JVM观察 RUNNING:2:1:0（无脏状态与孤儿审计）。
- 注入 COMMIT：事务 UPDATE + audit 正常提交，释放锁后旁观 JVM观察 PAUSED:3:1:1。
- 标准输出与错误输出分别保存在 `backend/target/native-mysql-jvm-diagnostics/`。
- 该测试 opt-in，默认 Maven 全量测试不会连接数据库；运行需设置 `CLIPFETCH_MYSQL_IT_PASSWORD` 环境变量并显式打开 `-Dclipfetch.mysql.twoJvm=true`、`-Dtest=NativeMysqlTwoJvmCommitIT`。

## 边界与下一阶段
- **双独立 JVM 的数据库事务+锁协议**经过验证，但子进程不是完整 Spring Boot ApplicationContext，也没有在本次测试里执行真实 Peer 下载、心跳定时续约、Spring TransactionTemplate 代理或双服务节点。
- MySQL 服务与两个 JVM 都运行在同一 Windows 主机；它不是两台物理机器跨网络/存储故障的验收。
- NFS/SMB 真实共享存储目前不支持，命中已知类型和 UNC 路径时拒绝所有权领取与 Piece 提交。
- 生产自动恢复/自动接管继续禁用。完整生产验收仍需要两个 Spring Boot JVM 连同一 MySQL，受控崩溃发生在事务提交前后，且覆盖 Worker 心跳、Piece IO、Checkpoint 复核、审计与超时清理。
